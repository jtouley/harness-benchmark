# cbench: a reproducible comparison of Cadence and other agent harnesses

`cbench` installs Cadence and five open-source alternatives at pinned commits,
then measures them with code. It doesn't rely on reading their READMEs. Every
committed number under [`results/`](results/) can be regenerated byte-for-byte
with one command:

```bash
cd bench
uv run --frozen python -m cbench fetch     # clone pinned SHAs, build (needs network once)
uv run --frozen python -m cbench verify    # recompute everything, byte-compare with results/
```

`verify` exits non-zero and prints a diff if any committed result can't be
reproduced. The generated tables are in [`results/REPORT.md`](results/REPORT.md).

## Arms

| Arm | Pinned in | Installed with |
|---|---|---|
| `baseline` | — | nothing (Claude Code alone; the control) |

| `cadence-fix` | `jtouley/cadence@0d4db70` (hook and install fixes, plus the R1 review fixes) | its `install.sh`, starting with no skills dirs |
| `superpowers` | `obra/superpowers@8ca22db` | copied as a Claude Code plugin dir (`--plugin-dir`) |
| `spec-kit` | `github/spec-kit@b9e08bf` | `specify init --integration claude` |
| `openspec` | `Fission-AI/OpenSpec@9111a76` | `openspec init --tools claude` |
| `gsd-core` | `open-gsd/gsd-core@83aba44` | `bin/install.js --claude --local` |
| `bmad` | `bmad-code-org/BMAD-METHOD@bda3c59` | every skill copied into `.claude/skills` (emulates `npx skills add`) |

Installers run for real into `/tmp/cbench/<arm>/{home,proj}` with a scrubbed
environment (fixed `HOME`, `TZ=UTC`, no proxies, telemetry off). The path is
fixed because some installers bake absolute paths into the prompts they write,
and those bytes are counted as tokens. Everything lives in
[`frameworks.lock.json`](frameworks.lock.json).

## The three tiers

**Tier 1, context footprint (deterministic).** For each install, `cbench`
discovers what Claude Code would load: skills, commands, agents, `CLAUDE.md`
memory, plus the text that SessionStart hooks inject (the hooks are actually
run). It reports:

- *always-on* tokens, paid on every request;
- the whole *corpus*;
- the documented *workflow* path, given as a lower and upper bound. Lower is each
  step's own file. Upper adds the step's `@file` references and its whole skill
  package.

Costs come from [`pricing.json`](pricing.json).

**Tier 2, golden hook probes (deterministic).** [`golden/probes/`](golden/probes/)
defines 10 scenarios. Examples: "edit `src/` before the plan is approved",
"forge the approval marker", "stop mid-execution", "read `.env`". Each framework
gets fixture files for each workflow state, in its own artifact layout. The
probe builds the exact JSON payload the host would send, runs every registered
hook, and classifies the result with an explicit rule table
([`cbench/hookrun.py`](cbench/hookrun.py)). Each verdict records the rule that
produced it (`via`), so a deliberate deny can be told apart from a hook that
crashed while registered fail-closed.

**Tier 3, live golden tasks (observed, then replayable).** Three golden tasks
live in [`golden/tasks/`](golden/tasks/): a bugfix, a CLI feature and a
spec-to-code module. Each has hidden tests and a reference patch, and
`golden-check` proves the hidden tests fail before the patch and pass after it.
`cbench live` runs `claude -p` with each framework installed and stores the
stream-json transcript, the final patch and a record with hashes. `cbench grade`
then rebuilds the exact base commit, applies the stored patch and runs the
hidden tests. Pass rates, token counts and dollar costs all come from those
stored files.

## What "deterministic" means here

| Deterministic and verified by `verify` | Not deterministic, and how it's handled |
|---|---|
| Framework sources (pinned SHA, checked after fetch) | Model sampling in live runs: treated as an observation. Run `--trials 3+` and compare medians. |
| Installs (each installed twice; normalized tree hashes must match) | Wall-clock time (recorded, never used in grades) |
| Token counts (tokenizer file pinned by sha256) | Spec Kit's npm/PyPI dependency drift: resolved with `uv lock --exclude-newer` at the commit date |
| Hook verdicts (fixed payloads, fixed env, no network) | |
| Grades and costs of recorded runs (rebuilt from stored patch + usage) | |
| The report (a pure function of `results/*.json`) | |

The tokenizer is the Claude tokenizer shipped in `anthropic==0.37.1`. It is an
older tokenizer, so Tier 1 counts are a stable proxy for comparing arms with
each other, not exact billing for current models. Tier 3 gives exact usage, and
its *first-request overhead vs baseline* column measures each framework's real
always-on cost as Claude Code sent it.

## Running the live tier

```bash
export ANTHROPIC_API_KEY=...
uv run --frozen python -m cbench live --trials 3 --model claude-sonnet-5-5 --max-budget-usd 5
uv run --frozen python -m cbench grade
uv run --frozen python -m cbench report
```

`live` prints the run count and the spend ceiling (runs × `--max-budget-usd`)
and asks before spending. Existing records are skipped, so an interrupted
matrix resumes where it stopped. Commit `results/runs/` so others can regrade.

## Findings so far (tiers 1 and 2)

These come from `results/` at the commits above. The bullets describe the
published `cadence` arm. `cadence-fix` (commit `0d4db70`) addresses the install
and hook bugs found here and scores 7/9 on both hosts, every block coming from
an explicit decision. S09 and S10 remain out of scope for that commit. Its
workflow upper bound is larger only because the skill root, which is the whole
repository, now also contains `bench/`.

- **Only two arms enforce anything in code: Cadence (Cursor only) and GSD Core
  (Claude Code).** Superpowers, Spec Kit, OpenSpec and BMAD register no hook
  that can block an action. Their discipline is instructions only.
- **Cadence registers no hooks under Claude Code.** `install.sh` merges hooks
  only into `~/.cursor/hooks.json`, in Cursor's schema. Under Claude Code every
  probe is `·` (no hook), which contradicts the README's "Claude Code:
  automatic via hooks".
- **Cadence under Cursor** denies S01 (an edit before approval) by an explicit
  `permission: deny`. Several other paths go through:
  - S03: shell edits (`sed -i src/...`) aren't matched.
  - S04: writing `.context/gates/entry-invariant.ok` yourself is allowed, and
    that file is all the edit gate checks.
  - S05: rewriting `.context/findings.jsonl` with `"status": "verified"` is
    allowed, bypassing `ledger_verify.py`.
  - S08: with no session, edits are allowed.
- **Cadence's stop guard doesn't speak Cursor's stop protocol.** It prints plain
  text and exits 1 (block), 2 (escalate) or 0 (allow), with no JSON
  `followup_message`. Under Cursor's documented rules, S06 is blocked only
  through `failClosed` (†), and S07, a stop *after* the run completed, is
  blocked too, because plain text is not valid JSON.
- **F1, a first-install bug in Cadence.** If `~/.cursor/skills` doesn't exist
  when `install.sh` runs, `link_skill` skips the `cadence` symlink, because
  `publish_peers` creates the directory only afterwards. `merge_hooks` still
  registers hooks at `~/.cursor/skills/cadence/hooks/*.py`. Python exits 2 on a
  missing script, which Cursor treats as deny, so every edit and every stop is
  blocked until `install.sh` is run a second time. Reproduce it by removing the
  `{home}/.cursor/skills` mkdir from the lockfile and running `cbench probes cadence`.
- **GSD Core** blocks S09 (secret read) and S10 (clobbering `ROADMAP.md`) and
  advises on the rest. Its workflow guard is off by default.
- **Footprint.**
  - Cadence's always-on cost is small: 455 proxy tokens, against 3,457 for GSD
    and 2,004 for BMAD.
  - Its workflow upper bound (40k) is large because the skill root is the whole
    repository.
  - GSD's workflow inlines up to 125k tokens through `@file` references.
  - At list prices, loading any framework's whole workflow costs cents. Whether a
    framework is worth its cost is decided by how it changes agent behavior,
    which Tier 3 measures.

## Limitations

- Cursor verdicts follow Cursor's documented hook semantics. No running Cursor
  binary was available, so they are not validated against one.
- BMAD's installer is a third-party CLI (`npx skills add`), so its install is
  emulated by copying every skill.
- The drive prompt that starts each framework (`drive_prompt` in the lockfile)
  is a choice. It is versioned, and its hash is stored in every run record.
- Three golden tasks are a small sample, and adding tasks is cheap. A task is a
  directory with `repo/`, `issue.md`, `hidden/` and `reference.patch`, plus a
  `task.json`. `golden-check` rejects any task whose hidden tests don't
  separate the untouched repo from the reference.

## Layout

```
bench/
  frameworks.lock.json   pinned arms, build + install recipes, drive prompts
  pricing.json           $/MTok per model (source and date inside)
  cbench/                harness (python -m cbench --help)
  golden/probes/         scenarios.json, states.json
  golden/tasks/          T01..T03: repo/, issue.md, hidden/, reference.patch
  results/               committed outputs + REPORT.md
  tests/                 unit + pipeline tests (scripted agent stands in for claude)
```

Tests: `uv run --frozen python -m pytest`. The pipeline tests use the canonical
sandbox root, so don't run them alongside another `cbench` command.
