# Experiment, iteration 4: two harnesses vs. one-shot Opus, Sonnet and Haiku

Date: 2026-10-11 to 2026-10-12. Status: exploratory, one run per cell (n=1), run outside this
harness, like [iteration 3](2026-10-10-harness-vs-oneshot.md). It is not a [criteria v1](../criteria.md)
result. Data: [`2026-10-12-iteration-4/`](2026-10-12-iteration-4/). Synthesis for readers who
want the conclusions: [`../findings.md`](../findings.md).

## Question

Iteration 3 ran both harnesses on Opus, and the baselines on Sonnet and Haiku only. So it could
not tell "the harness helped" from "Opus is a stronger model". Iteration 4 adds the missing cell:
**Opus alone, with the same prompt and the same tools.**

## Arms

| Arm | Model | Process | Prompt |
|---|---|---|---|

Templates H and B are word for word the ones in [iteration 3](2026-10-10-harness-vs-oneshot.md#template-h-harness-arms).
Template B is Template H with the skill line, the slash command and every pipeline word removed.
Nothing is added to it. The task text is the same, word for word, for every arm. The tasks are
T04–T06 of this repository (`golden/tasks/T0[456]*`): multi-currency, monthly budgets, and audit
trail with undo for `ledgerlite`, a ~300-line Python CLI. Each agent was a Claude Code
`general-purpose` subagent on macOS with the same tools, started from the same baseline commit
by [`setup_iteration.sh`](2026-10-12-iteration-4/setup_iteration.sh). To repeat the round, build a
workspace with [`make_workspace.sh`](2026-10-12-iteration-4/make_workspace.sh), then run
`setup_iteration.sh` in it. The two Cadence reruns used `ARMS=with_skill_fixed`.

## Changes from iteration 3

1. **Opus one-shot added.** This is the control that iteration 3 lacked.
2. **Cadence moved from `6abc622` to `335154d`.** That includes cadence#52 (orchestrators cannot
   write their own verdicts, run-scoped gates, a PR guard) and cadence#57 (a fix for #52).
3. **A Cadence defect hit the first runs.** At `8ffbf6a` (#52), the hook wrote the orchestrator
   note to the Bash working directory of the subagent, which Claude Code resets to the parent's
   project before each call (cadence#56). In 2 of 3 Cadence runs the note was lost. Then every
   peer gate failed closed. cadence#57 fixed the defect, and those two tasks ran again. The
   results use the reruns. The pre-fix runs are reported apart, below.
4. **Blind folders use the delivered working tree.** Two Haiku runs never committed their work,
   so an archive of their branch would have graded the starting code.
   [`build_blind.py`](2026-10-12-iteration-4/build_blind.py) copies the working tree, removes
   harness names, ticket ids, phase labels and review finding ids from comments, then runs each
   folder's own tests (all pass after the scrub).
5. **Grader prompt.** It is the iteration-3 prompt with two changes. The number of solutions is
   4 to 6 per task. "All pass the same hidden tests" became "hidden acceptance tests are scored
   separately", because two Haiku solutions fail one hidden test.

## Measurement

- **Hidden tests (M1):** [`grade.py`](2026-10-12-iteration-4/grade.py) on the delivered tree.
- **Blind quality (M7, with reproduced defects as in M2):** one Opus grader per task saw every
  arm as an anonymous folder (final `ledgerlite/`, `tests/`, a diff from the baseline). It scored
  design, correctness, readability and tests from 1 to 10, and it had to reproduce each defect
  with a command. Scores, defects and rankings: [`blind_scores/`](2026-10-12-iteration-4/blind_scores/).
  Letter to arm: [`blind_mapping.json`](2026-10-12-iteration-4/blind_mapping.json).
- **Process checks (C1–C10):** `grade.py`. They apply to the harness arms. The one-shot arms fail
  most of them by design and are not compared on them. The denominator is 10 when the run left a
  session record and 9 when it did not (one check reads the session).
- **Severity of defects (M2):** the grader reproduced each defect. We assigned severity from its text
  by a written rule: major is a traceback or a breach of a sentence in the task spec, minor is anything
  else, and an undelivered run counts as one critical defect ([criteria v1 §6](../criteria.md#6-decision-rule-pre-registered)).
  The classification is in [`defects.json`](2026-10-12-iteration-4/defects.json). Criteria v1 wants a
  script and two reviewers for this. This round had neither.
- **Audit trail (M10):** counted from each repository's `.context/` and git history:
  [`auditability.json`](2026-10-12-iteration-4/auditability.json).
- **Cost (M9):** wall time and the token count in the completion notice of the run agent. The
  notice gives no input, output or cache split, so this round reports no dollars. Harness token
  counts are lower bounds (see Confounds).

## Findings

1. **No quality gain from a harness was shown.** Opus alone scored highest (8.00, against Cadence 7.33
   and ship-feature 7.88), with every hidden test, in about 1/30 of the wall time and 1/4 of the
   tokens. On two of three tasks the gap is inside single-run noise. The data supports "no gain shown",
   not "a loss".
2. **Fewer defects was not shown either.** Cadence had 0.67 major or critical defects per attempted
   run, against 1.00 for Opus alone. The pre-registered rule needs a gap of at least 0.5, with more runs.
3. **No crash reached either harness's delivered code.** Each one-shot (Opus, Sonnet, Haiku) shipped two
   reproduced tracebacks, all on budgets: a NaN amount, a tiny limit, a NaN limit. Cadence's own reviews
   caught and fixed a similar crash before delivery ([`cadence_ledgers/budgets.jsonl`](2026-10-12-iteration-4/cadence_ledgers/budgets.jsonl)).
   This is one task and one run per cell.
4. **Cadence builds beyond the spec, and the graders mark it down.** Multicurrency 6.75 (design 6:
   overflow handling and header normalization that the spec did not ask for). On audit-undo the grader
   called it "very robust" and "heavier than needed", and noted that it skips the log entry for an
   empty import. Iteration 3 had the same finding.
5. **Cadence finished every task with evidence. ship-feature did not.** ship-feature stopped on
   audit-undo at its 2-cycle plan-review limit. Cadence passed every gate from A1 to R7 on all three
   tasks after #57, and closed each must-fix finding with a verification record.
6. **Cadence failed closed when it broke.** The cadence#56 defect made two runs lose their orchestrator
   note. Both runs recorded a hard stop with the reason, and neither reported a pass. That is the M3
   property (no false success), seen on a real defect.
7. **Haiku 4.5 alone is not close.** It delivered 1 of 3 tasks, with spec failures that the hidden tests
   miss in the others too: no monthly conversion, audit lines that print the command twice, an undo chain
   that blocks itself.

## Confounds and limits (read before citing)

- **The one-shot baselines could see the user-installed skills.** Every Claude Code session listed 96
  skills with their descriptions: 67 installed by the user, some of which describe TDD, and 29 that every
  session gets. A transcript check ([`clean_room.json`](2026-10-12-iteration-4/clean_room.json)) shows that
  no one-shot called a skill or touched a skill, rule, command, plugin or memory location by a tool path.
  That check did not look at two other channels: instruction files the host loads into the session (the
  runs started from the Cadence checkout, whose `AGENTS.md` Claude Code may load) and user-level subagent
  types. The current check reads both; these transcripts were not re-checked with it. A description can
  still prime a model, so the baselines were not fully neutral. That bias, if any,
  favors the one-shots, which wrote tests unasked. The next run set uses a clean room
  ([process](../process.md#clean-room)).
- **The Cadence arms' review peers ran user-level skills.** The check of the nested agents shows peers
  calling skills by peer name (`vibe-test`, `test-benchmark`, `pr-review-local`, ...). With Cadence not
  installed as a plugin, those names reached user-level skills, not Cadence's bundled peers (cadence#53).
  The orchestrators then sent the peers the bundled paths. A clean room removes this.
- **n = 1 per cell, one grader per task.** A difference under about 1 quality point is inside
  single-run noise. Criteria v1 requires 5 runs per cell and two graders.
- **The tasks are class S** ([criteria §3](../criteria.md)): small and precisely specified. A
  model alone should do well on them. The result says nothing about class L or O tasks, where a
  harness should earn its cost.
- **"One-shot" is a tool-using agent,** not one completion. Opus used 11–16 tool calls.
- **Shadowed peers (cadence#53).** User-level skills named `pr-review-local`, `test-benchmark` and
  `vibe-test` ran in place of the bundled Cadence peers. The Cadence orchestrators then sent the
  peers the bundled paths. Both harness arms ran with this setup.
- **ship-feature sandbox limits.** The host denied reads of `~/.cursor/skills/_shared`, so
  ship-feature ran some gate scripts by hand.
- **Cadence multicurrency** ran before #57. It wrote its own orchestrator note to get past
  cadence#56, then resumed. Its gates and reviews are otherwise normal. Its 6.75 stays in the table.
- **Token counts.** The run agent's completion notice may not include nested subagents. Treat the
  harness counts as lower bounds. Wall time is reliable.
- **Environment.** Claude Code subagents on macOS, no GitHub. The PR flow is simulated in `PR.md`.
