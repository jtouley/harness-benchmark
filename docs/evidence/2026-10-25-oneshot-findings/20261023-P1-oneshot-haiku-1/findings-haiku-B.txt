FINDINGS
--------

F1 [HIGH, reproduced] A crash during a flush loses events on the next run (or duplicates them).
    Where: ingest/stream.py, Consumer.__init__ and flush().
    The docstring and DECISIONS #24 say: "if the process dies before a load, those events were never landed, and
    the next run reads them again." Not true. A kill after dlt's extract step leaves a pending load package in
    out/dlt. On the next run, read_lake_state() runs first and does not see those events, so the consumer
    re-consumes them from the stream. Then the first flush's pipeline.run(rows) LOADS THE OLD PACKAGE AND DROPS
    `rows`. dlt logs only a WARNING: "The pipeline `run` method will now load the pending load packages. The data
    you passed to the run function will not be extracted." flush() still adds len(rows) to the landed count, and
    seen and last_sse_id have already moved on, so those events are gone for good.
    Repro: I left a 300-row extract-only package (the next 300 events, seq 1129-1428) and ran
    `make stream DURATION=3`. The lake ended with 1,991 rows. Capture positions 1428-1627 (200 events) are
    missing. _arrival_seq jumps from 1428 to 1629. The run printed "landed 1063" and dbt still passed 104/104.
    If the pending package is larger than the first batch, you get duplicate meta_ids and arrival_seqs instead.
    Fix (tested; after the fix the same simulation gave no new loss, no duplicates and no seq gap):
        self.pipeline = stream_pipeline()
    +   if self.pipeline.has_pending_data:
    +       # A previous run died mid-flush. Finish its package first, so the lake state below includes it.
    +       self.pipeline.run()
        self.seen, self.last_sse_id, self.next_seq = read_lake_state()
    Also suggested: in flush(), check that the returned LoadInfo contains this batch, and fail loudly if not.

F2 [HIGH if the grader runs in place, reproduced] The incremental state lives outside out/, so the marts can stop
    matching the lake.
    Where: transform/profiles.yml is `path: out/warehouse.duckdb`, which resolves to transform/out/warehouse.duckdb.
    The incremental store_* tables live there. The repo's own .gitignore says the grader removes lake/ and out/.
    Neither of those holds this file.
    Repro: make build; make stream DURATION=6 (3,455 events). Then rm -rf lake out; make build;
    make stream DURATION=3. The lake now has 1,128 rows, but fct_edit still shows 1,899 edits with
    max(arrival_seq)=3455, the old data. The incremental filter `arrival_seq > max(...)` drops every new row
    (new seqs restart at 1). dbt still passed 104/104. The author hit this too (transcript: "rm -rf transform/out &&
    make build" after the canary fix), but DECISIONS #29 only covers the opposite case (warehouse missing).
    Fix (tested): set profiles.yml to `path: ../out/warehouse.duckdb`. The same scenario then gives lake 793 and
    fct_edit max seq 793. For the case where only lake/stream is removed, also make store_arrivals fall back to a
    full rebuild when max(_arrival_seq) in the lake is below max(arrival_seq) in {{ this }}.

F3 [HIGH, reproduced] Empty stream marts publish an all-NULL row, so oracle check 7 says 1 when the answer is 0.
    Where: every external model. dbt-duckdb 1.11.0's external.sql inserts one NULL row into empty results before
    writing the file, then reads the file back through a view that filters that row out. That is why the
    not_null and unique tests pass while the published Parquet holds a NULL key.
    Repro: rm -rf lake out transform/out; make build; make stream DURATION=4 (1,500 events, none late). Then the
    oracle_map check 7 query returns [(1,)], and late_events.parquet holds one row of 11 NULLs. After `make build`
    alone, fct_edit, late_events and mart_edit_window_5m each hold one NULL row. DECISIONS #28 documents the quirk
    and tells analysts to filter, but oracle_map.yml's own queries do not filter. Both "every mart has events
    after make stream" and "count of late events" depend on DURATION, which the grader picks.
    Fix (tested, with PASS=119 and the extra tests below): override the materialization in the root project. Copy
    .venv/.../dbt/include/duckdb/macros/materializations/external.sql to transform/macros/external_no_null_row.sql
    and delete this block:
        -- if relation is empty, write a non-empty table with column names and null values
        {% call statement('main', language='sql') -%}
          {% if row_count[0][0] == 0 %}
          insert into {{ temp_relation }} values ( ... NULL, ... )
          {% endif %}
        {%- endcall %}
    Result: late_events.parquet has 0 rows and keeps its typed schema (event_key VARCHAR, arrival_seq BIGINT, ...).
    Then update DECISIONS #28.

F4 [MEDIUM, reproduced] A disconnect inside a multi-byte UTF-8 character crashes `make stream` instead of resuming.
    Where: sse_events(): `line = raw.decode("utf-8")`. When the connection ends mid-line, urllib yields the partial
    last line. If the cut falls inside a multi-byte character, decoding raises UnicodeDecodeError. That is a
    ValueError, which the author removed from the reconnect `except`, so it escapes run() and the make exits
    non-zero. dbt does not run.
    Repro: a local server sends one good event, then `data: {..."title":"Do\xc3` and closes. sse_events yields
    x1, then raises UnicodeDecodeError ("unexpected end of data"), which the consumer's
    (OSError, HTTPException) handler does not catch. My proxy run (C8) only got lucky on byte boundaries.
    jawiki, dewiki, frwiki and itwiki titles and comments are full of multi-byte characters, so in a live demo
    with real disconnects this is likely.
    Fix: ignore a trailing line that has no b"\n" (it is incomplete by definition): `if not raw.endswith(b"\n"):
    break`. Or decode with errors="replace", or add UnicodeDecodeError to the reconnect except.

F5 [MEDIUM, reproduced] `make build` is not byte-idempotent, and the lake changes on every build.
    Two back-to-back builds with nothing changed: the md5 of dim_place, mart_obligations_monthly and
    mart_obligations_fy_county differs (row order; the models have no ORDER BY and run with threads: 4). The
    lake also gets a new parquet file name and a new _dlt_load_id value per table, plus one more
    lake/raw/_dlt_loads/*.jsonl file per build (33 files, then 34). The author compared sorted row hashes, and
    DECISIONS #31 calls the result "byte-identical", which it is not. The spec says "must not change any output".
    Fix: add `order by <grain key>` to every mart model's final select (DuckDB keeps insertion order in COPY).
    Either accept the dlt metadata churn in the lake and state it in DECISIONS, or narrow the #31 claim.

F6 [MEDIUM, reproduced] `make stream` fails on a clean checkout without `make build` first.
    rm -rf lake out transform/out; make stream DURATION=2: it lands 325 events, then the dbt build fails on all
    staging models over lake/raw, and make exits 2. The stream target runs a full `dbt build`.
    Fix: in the stream target, run `dbt build --select stg_recentchange+ dim_wiki`. That is also faster, because
    the batch models stop rebuilding on every stream run. Or have the stream target depend on the batch lake.
