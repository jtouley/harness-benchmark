## Scenarios traced through the spec

S1. Analyst runs `make build` twice. The spec says outputs must not change. It does not say what is compared, and the lake keeps "load metadata", which normally includes a load timestamp. Result: unverifiable as written (see G-8).

S2. The consumer crashes after writing a micro-batch but before committing its position. The spec requires that no event is lost or counted twice. The spec does not say where the position lives or how the data write and the position commit become one step, and it names no event identity to dedupe on (see G-7).

S3. A redelivered event arrives after a reconnect. The late rule uses "at its first arrival". The spec gives no dedupe key and does not say the running maximum event time survives a restart (see G-7).

S4. An edit arrives 11 minutes after its window ends, after a newer event has already arrived. The late rule is clear here: late when the highest prior event time is more than window end + 10 minutes. The spec does not say whether the edit fact keeps late events. Check 5 counts late edits, and the window mart must exclude them, so the fact must hold them (see G-6).

S5. Analyst runs check 4 for one month and the source includes foreign or unassigned place-of-performance rows. The spec does not say how county or state is set for those rows, so county totals cannot be shown to add up to state totals (see G-1, G-2).

S6. Analyst runs check 3 and gets a count of awards. Each USAspending row is one transaction, and an award spans many transactions. The spec does not define "award" (see G-3).

S7. A county has no 2024 estimate. The amendment gives a fallback to the latest earlier estimate. The spec does not say what happens when no earlier estimate matches (see N-1).

## Blocking gaps

G-1: The spec does not choose the county and state for "where the money went". USAspending rows carry both a recipient county FIPS and a place-of-performance county FIPS. The spec also has no bucket for rows with no county, so check 4 (county totals = state totals = source total) has no defined sum.

G-2: "Month" is undefined. The source has `action_date` and `action_date_fiscal_year`. FY2024 runs October 2023 to September 2024. The spec does not say whether the monthly mart uses the calendar month of `action_date` or the fiscal month.

G-3: "Award" in check 3 is undefined. The count could be per transaction row or per award (for contracts `award_id_piid`; for assistance an award key). The two give different answers.

G-4: The per-person measure in the monthly mart is undefined. It is not stated whether obligations per person is a monthly amount divided by the July 1, 2024 population, or an FY2024 amount. It is also not stated how population rolls up from county to state and agency. Summing population across agency rows would double count.

G-5: "Summed exactly" has no type. The spec does not give a decimal precision and scale for obligations, or a rounding rule for per-person division. The dbt model contract cannot enforce column types without them.

G-6: Check 5 depends on what counts as an edit. The spec does not say which `type` values count (edit, new, log, categorize), or how null `length` values are treated in net bytes. The spec also does not say whether the edit fact includes late events, or whether late classification runs in the engine at ingest or in dbt. First-arrival classification needs history across micro-batches, so the placement matters.

G-7: The stream rules need two things the spec does not give. (a) An event identity for dedupe (the event `meta.id` is the obvious candidate, but not named). (b) The rule that the running maximum event time is stored with the consumer position in the same commit. Without (b), late classification changes after a restart, and the late rule cannot hold across "stop and start".

G-8: The exit criterion "running make build twice must not change any output" has no comparison rule. Byte equality of Parquet fails if writer metadata or load timestamps differ. The spec must say whether comparison is by row content and which columns (load metadata) are excluded from marts.

G-9: No make target is named for building the stream dbt models. `make build` "runs the batch part" and `make stream` "updates the stream tables". The spec does not say which target runs `dbt build` for the edit fact and window mart, or what `make stream` does when the replay ends before DURATION.
