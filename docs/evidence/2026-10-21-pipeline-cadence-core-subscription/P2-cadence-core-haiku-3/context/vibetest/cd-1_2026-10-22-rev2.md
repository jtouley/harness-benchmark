## Scenarios traced through the spec

S1. Analyst runs `make build` twice. The spec requires no output change. It does not say how outputs are compared, and the lake adds "load metadata", which usually includes a load timestamp. Result: cannot be verified as written (G-8).

S2. The stream consumer writes a micro-batch, then crashes before it commits the position. The spec requires no loss and no double count. It does not say where the position is stored, or how the data write and the position commit become one step. It names no event identity to dedupe on (G-7).

S3. After a reconnect, the replay redelivers an event already consumed. The spec gives no dedupe key. The late rule is defined "at first arrival", so a redelivered event needs a rule. The spec does not say that the running maximum event time survives a restart (G-7).

S4. An edit arrives 11 minutes after its window ends, after a newer event has already arrived. The late rule applies cleanly here. The spec does not say whether the edit fact keeps late events. Check 5 counts late edits, and the window mart must exclude them, so the fact must hold them. The spec does not say which layer (engine at ingest, or dbt) classifies lateness. The rule needs history across micro-batches, so the placement matters (G-6).

S5. Check 4 runs for one month. The USAspending rows include recipient and place-of-performance locations, some foreign or with no county. The spec does not say which location sets county and state, or where rows with no county go. County totals cannot be shown to add up to state totals as written (G-1).

S6. Check 3 counts "awards with a net negative obligation". Each source row is one transaction, and one award has many transactions. The spec does not define "award" (G-3).

S7. Check 1 and check 2 use "FY2024 net obligations". The spec does not say whether the month is calendar or fiscal, or whether the monthly mart's per-person value is a monthly or FY amount (G-2, G-4).

S8. A county has no 2024 estimate. Amendment A says to use the latest earlier estimate. The 2024 file already holds 2020 to 2024 columns, so the fallback can be found in the same file. The spec does not say which file or column the fallback uses (N-1).

S9. Check 5 is "the replayed hour". The spec does not say which hour, or how it relates to `DURATION` or to the replay's event times (G-10).

S10. The analyst reads the engine section and the stack output. The engine section says "as the shared spec says", and output 3 says "plus whatever the stack section asks for". Neither section is in the snapshot (G-11).

S11. Someone adds a new mart. The engine section says a new mart of the same kind "needs YAML only, no Python". The architecture section puts every model after the lake into dbt SQL. These two rules do not agree on where a mart is defined (G-12).

## Blocking gaps

G-1: The spec does not choose the county and state for "where the money went". USAspending rows carry a recipient location and a place-of-performance location. The spec has no bucket for rows with no county, so check 4 has no defined sum for county against state.

G-2: "Month" is undefined. The source has `action_date` and `action_date_fiscal_year`. The spec does not say whether the monthly mart uses the calendar month of `action_date` or the fiscal month.

G-3: "Award" in check 3 is undefined. The count could be per transaction row, per contract `award_id_piid`, or per assistance award key. These give different answers, and the spec does not pick one.

G-4: The per-person measure in the monthly mart is undefined. It is not stated whether obligations per person is a monthly amount divided by the July 1, 2024 population, or an FY2024 amount. It is also not stated how population rolls up from county to state and agency. Summing population across agency rows would double count.

G-5: "Summed exactly" has no type. The spec gives no decimal precision and scale for obligations, and no rounding rule for the per-person division. The dbt model contract cannot enforce a column type without them.

G-6: Check 5 depends on what counts as an edit. The spec does not say which `type` values count (edit, new, log, categorize). It does not say how null `length` values enter net bytes. It does not say whether the edit fact includes late events, or whether lateness is classified in the engine at ingest or in dbt.

G-7: The stream rules need two things the spec does not give. (a) An event identity for dedupe. The event `meta.id` is the likely candidate, but the spec does not name it. (b) A rule that the running maximum event time is stored in the same commit as the consumer position. Without (b), late classification can change after a restart, and the late rule cannot hold across "stop and start".

G-8: The exit criterion "running make build twice must not change any output" has no comparison rule. Byte equality of Parquet fails when writer metadata or load timestamps differ. The spec must say whether comparison is by row content, and which load metadata columns are excluded from the marts.

G-9: No make target is named for running dbt on the stream models. `make build` "runs the batch part" and `make stream` "updates the stream tables". The spec does not say which target runs `dbt build` for the edit fact and the window mart. It does not say what `make stream` does when the replay ends before `DURATION`.

G-10: Check 5 asks for "the replayed hour". The spec does not say which hour is meant: the first hour of the capture, the hour the consumer ran, or the first `DURATION` seconds. The exit criterion for check 5 cannot be tested without this.

G-11: The spec refers to two sections that are not in the snapshot. Output 3 says "plus whatever the stack section asks for". The engine section says DataFusion and Polars are on the ingestion side "as the shared spec says". Deliverables and the stack choice are not fully stated.

G-12: Conflict. The engine section says a new source or mart of the same kinds "needs YAML only, no Python". The architecture section says every model after the lake is a dbt project. A dbt model is SQL plus a YAML contract, so the spec does not say whether a new mart is a dbt model or an engine YAML entry.
