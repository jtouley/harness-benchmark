[F2] MEDIUM-HIGH. After a crash, the consumer reads events and then drops them without any error.
  - Why: if the process dies between dlt normalize and load (Ctrl-C or SIGKILL during _flush, OOM), a
    pending package stays in out/dlt-stream. On the next start, StreamConsumer builds `seen` and the
    checkpoint from the lake, which does not include the pending package. On the first _flush,
    pipeline.run() loads ONLY the pending package. dlt logs "The data you passed to the run function will
    not be extracted". _flush then clears _pending_raw and sets last_landed_id as if the batch had landed.
  - Verified (review_t1C/w/pending.py with the FakeReplay harness): run 1 lands events 1-3. I then left
    events 4-5 as a pending package and restarted against a replay of 1-10. Result: stream_raw = 1..5.
    Events 6-10 were read, accepted into `seen`, and lost. last_landed_id moved past them, so reconnects
    in the same run do not fetch them again. The marts built in that `make stream` miss them. The next
    process start recovers them, because the checkpoint on disk is still event 5. This breaks the A-stop
    claim in DECISIONS ("no event that it read is lost").
  - FIX (I verified it in the scratch copy; the stream and lateness tests still pass, 19/19): in
    StreamConsumer.__init__, create self._pipeline BEFORE reading seen and the checkpoint, then add
        if self._pipeline.has_pending_data:
            self._pipeline.load()
    With the fix the same scenario lands 1..10 with no duplicates. Optionally, _flush can also check
    has_pending_data after run() and raise. pipeline/batch_load.py has the same exposure: after a crashed
    build, the next build loads the stale pending package, ignores the fresh extract and exits 0. There a
    pipeline.load() before run(), or dropping pending packages, fixes it.

[F3] MEDIUM. If the stream endpoint is down or wrong, the consumer says nothing and exits 0.
  - Why: _read_until has `except OSError: return`, and _connect raises OSError for a non-200 status.
    Nothing is logged, and run() retries every second until DURATION ends.
  - Verified: STREAM_URL=http://127.0.0.1:1/nope gives rc=0, no output, no lake. STREAM_URL=
    http://localhost:8099/wrong/path (HTTP 404) gives rc=0, no output.
  - Effect: on a fresh lake, `make stream` then fails later in dbt with a confusing DuckDB "No files
    found" error for stream_events. On an existing lake it "succeeds" and republishes stale marts, so
    nobody notices the outage.
  - Suggested fix: log each connect failure to stderr with the reason (HTTP status or errno). Exit
    non-zero if no connection succeeded during the run, or treat 4xx as fatal right away.
