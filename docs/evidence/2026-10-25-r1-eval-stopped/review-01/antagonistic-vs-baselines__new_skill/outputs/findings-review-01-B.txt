BOTTOM LINE
-----------
The batch half (USAspending + Census + sitematrix into marts 1-4 and 8) looks sound. Every number I could
recompute from the raw files agrees with the design, and the source facts in DECISIONS.md check out.
The stream half is where the risk is. The consumer crashes on malformed-but-parseable input, which
contradicts its own docstring. The check 7 oracle never runs under either make target. Several stated
behaviours (flush cadence, stop at DURATION, what stream_raw contains) are overstated. Do not sign off on the
stream half until findings 1-4 are fixed or explicitly accepted.

SEVERITY KEY: High = wrong result, crash of a normal run, or a test that gives false comfort.
              Medium = real defect with bounded impact or a stated guarantee that does not hold.
              Low = robustness, docs, or hygiene.

1. [HIGH] Check 7 test never runs under either make target. False comfort.
   Where: /var/tmp/revieweval/.../repo/transform/tests/test_late_events_count.sql line 11
          (`read_parquet('out/marts/late_events/*.parquet')`), no ref() to late_events.
   Evidence (verified):
   - build.log has no line for test_late_events_count. The stream run (`make stream DURATION=90`,
     `dbt build --select +mart_window_5min +late_events +edits_by_wiki_actor`) lists 15 nodes, and this
     test is not among them. The build run's test list is also missing it.
   - `dbt ls --select +mart_window_5min +late_events +edits_by_wiki_actor --resource-type test` does not
     list it. `dbt ls --select +mart_monthly_obligations +mart_award_fy2024 --resource-type test` does not
     list it either.
   - Cause: the test reads the mart through read_parquet, not ref(), so dbt has no edge to late_events and
     the +late_events selector does not reach it.
   Consequence: check 7 (late event count) has no executed oracle. DECISIONS.md lines 117-120 say three
   stream tests cover checks 5, 6 and 7. Only two run.
   Fix: replace the read_parquet with {{ ref('late_events') }} and re-run dbt ls to confirm the test is
   selected. Also make sure the build log shows it PASS.

2. [HIGH] Consumer crashes on malformed-but-parseable input. The docstring promises it will not.
   Where: pipeline/stream_consumer.py
     - line 66 (`raw.decode("utf-8")` inside iter_sse), called from the for loop at line 162. The outer
       try (line 171) catches only OSError and http.client.HTTPException, so UnicodeDecodeError escapes.
     - line 200 (`if event_id in self.seen`): meta.id that is a list or dict raises TypeError.
     - line 206 (`if row["type"] in EDIT_TYPES`): a list-valued type raises TypeError.
     - lines 176-189 (_connect) catch only OSError; a bad status line raises http.client.BadStatusLine
       (an HTTPException), which escapes because the caller at lines 157-160 also catches only OSError.
   Evidence (verified by running the probe script against a local server, temp lake):
     invalid UTF-8 byte in a data line  -> CRASH UnicodeDecodeError
     meta.id = ["x"]                    -> CRASH TypeError: unhashable type: 'list'
     type = ["edit"]                    -> CRASH TypeError: unhashable type: 'list'
     "HTTP/1.1 garbage" status line     -> CRASH BadStatusLine
     In each case the next good event in the same stream never lands.
   Why it matters: a crash ends the run early. `make stream` then fails before its dbt step. The module
   docstring for _skip (line 271) says the design is that "one bad event does not stop the stream". The
   tests cover only wrong-typed length and timestamp (test_stream_consumer.py line 69), so this gap is
   untested.
   Fix: validate meta.id and type are strings in _field_problem. Decode with errors="replace", or catch
   UnicodeDecodeError per line and skip it. Catch HTTPException in _connect and in _read_until. Add a test
   for each case.

3. [MEDIUM] Wrong-typed fields are silently coerced or nulled. Some are not logged at all.
   Where: pipeline/stream_consumer.py _field_problem (lines 253-267) checks only timestamp and length.
   Evidence (verified):
     namespace = "Talk"  -> lands with namespace NULL, no skip message
     namespace = "0"     -> lands as 0 (dlt coerces to the bigint column)
     wiki = 123          -> lands as the string "123"
   Read from code, not run: flatten (line 91) uses bool(event.get("bot")) for the bot column, but
   actor_type (line 94) uses `is True`. So bot = "false" gives bot = True and actor_type = "human". The two
   columns disagree.
   Why it matters: a NULL namespace is part of window_5min's unique key
   (transform/models/star/window_5min.sql line 3). NULL keys do not collide in a merge, so incremental
   duplicates are possible. I did not run dbt to confirm; the schema test (GROUP BY) would catch them only if
   they materialise.
   Fix: validate namespace (int or null), wiki (string), bot (bool), and reject the event with a logged
   skip rather than coercing.

4. [MEDIUM] A silent stream overruns DURATION by the socket timeout.
   Where: pipeline/stream_consumer.py _lines (lines 275-281) checks the deadline only between lines, and
   readline (line 278) blocks for up to SOCKET_TIMEOUT (5.0 s, line 25).
   Evidence (verified): one event, then no heartbeats and no EOF, DURATION = 0.5 s -> run() returned after
   5.52 s (socket_timeout 5.0).
   The unit test test_consumer_heartbeatsOnly_stopsAtDuration covers heartbeats only, so it does not catch
   this. DECISIONS.md line 79 and the `make stream` default (60 s) imply the run stops on time.
   Fix: give each readline a timeout of min(socket_timeout, deadline - now), or drive reads with select()
   against the deadline. Add a silent-stream test.

5. [MEDIUM] `make stream` results depend on run history, not only on DURATION.
   Where: DECISIONS.md lines 103-107 and 113-116. _accept/flush append to lake/stream_raw, and _connect
   resumes from the checkpoint (lines 182-183). A second `make stream` continues the same replay.
   Evidence: the build log's make stream run (DURATION=90) runs on whatever lake already exists. The stream
   marts and checks 5-7 are cumulative. DECISIONS.md says so (line 107, "a later make stream run adds to
   them"), but the "replayed hour" in A-18 becomes "whatever this lake holds", not a fixed hour.
   Fix: either make the stream step start from an empty lake (or take an explicit lake-reset flag), or state
   in the Makefile and in the answer which run defines the hour. Do not leave it implicit.

6. [MEDIUM] Oracles share code with the models, so most tests check consistency, not correctness.
   Evidence (read from code, confirmed by grep):
     - usaspending_raw() (transform/macros/usaspending_raw.sql) is used by stg_usaspending_awards and by the
       oracles for checks 1, 2, 3 and 4. A wrong column mapping (for example award_key or the place codes)
       passes every test.
     - test_top_ten_counties_per_person.sql line 18 takes population from dim_place, which is the model
       whose population rule (Amendment A, the 2021 fallback) the test is supposed to check.
     - The late rule is written twice (lateness.py and stream_raw_arrivals.sql) from the same reading of the
       spec. The tests check that the two agree. They do not check that the reading is right (for example,
       whether high-water includes non-edit events, and whether exactly 600 s is late).
   Mitigation I did run: I recomputed checks 1 to 3 in Python directly from the raw CSVs and Census files,
   with no SQL and no shared macro (values below). The author can compare these to out/marts directly.
   Fix: add one oracle that is not built from the repo's macros, or at least say in DECISIONS.md which
   answers are only cross-checked for consistency.

8. [LOW] A checkpoint can be reset to null, which drops Last-Event-ID on the next connection.
   Where: pipeline/stream_consumer.py line 212 (`_pending_last_id = sse_id`) and line 242
   (`last_landed_id = _pending_last_id`).
   Evidence (verified by a local server): an event with no `id:` line, received after an event with id a1,
   leaves the next connection with no Last-Event-ID (headers: None, a1, None, c3...). Events in the gap would
   be lost. The real stream always sends an id, so the likelihood is low.
   Fix: keep the last non-null id: `if sse_id is not None: self._pending_last_id = sse_id`.
