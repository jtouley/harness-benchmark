VERDICT: CHANGES REQUESTED

The batch half (checks 1 to 4) is in good shape, and its numbers hold up against the raw data.
The stream half has a required check that no make target runs, a crash path that breaks the
"one bad event does not stop the stream" rule, and a stream-scope problem: checks 5 to 7 cover
everything the lake has ever landed, not the replayed hour the spec asks about.


BLOCKING
--------

B1. Check 7 (late events count) is never executed by any make target.
    Where : transform/tests/test_late_events_count.sql; Makefile (stream target)
    Why   : The test reads out/marts/late_events/*.parquet and lake/stream_raw via
            read_parquet/stream_raw_arrivals() with no ref() to a model. `dbt build --select
            +mart_window_5min +late_events +edits_by_wiki_actor` only runs tests attached to selected
            nodes, so this one is dropped.
    Proof : The stream build log lists 15 of 15 nodes. The singular tests that ran are
            test_stream_totals_per_wiki, test_top_windows_en_wikipedia and
            test_event_time_utc_is_utc. test_late_events_count does not appear. The batch target
            likewise never runs it. DECISIONS.md says the quality gate passes; for check 7 it
            does not run at all.
    Ask   : Make the test reachable from the DAG (for example, a ref() to late_events in the test,
            or a dbt-invoked test list) and show it in the stream log. Alternatively run it in a
            make target and fail the target on failure.

B2. Checks 5 to 7 answer "all landed data", not "the replayed hour".
    Where : DECISIONS.md "Stream models and marts", "Data step"; pipeline/stream_consumer.py
            (read_column of checkpoint, Last-Event-ID resume, _connect); the oracle macro
            transform/macros/stream_raw_arrivals.sql reads lake/stream_raw/*.parquet in full.
    Why   : The consumer resumes from the checkpoint on every start (self.last_landed_id,
            sent as Last-Event-ID). Each make stream therefore continues the replay where the
            last run stopped, and the lake accumulates. Nothing filters the stream marts by run.
            DECISIONS says "the replayed hour is every event that this run landed", which is only
            true for one fresh run. The build log shows a 90 s stream run on this same tree
            (make stream DURATION=90), and DECISIONS cites a 3600 s run on a fresh lake that is not
            in the log. If both are in the lake, the stream marts hold the union.
    Ask   : Either record a run id on stream rows and scope the marts and oracles to the run the
            spec means, or have make stream start from an empty stream lake so the output is
            reproducible, or state exactly which run the grader will see and make the lake match.

B3. A malformed event crashes the consumer.
    Where : pipeline/stream_consumer.py line 206 (`if row["type"] in EDIT_TYPES`); _field_problem
            (lines 253-267) does not check `type`, `wiki`, `server_name` or `namespace`.
    Proof : Probe with an event whose "type" is ["edit"]:
              StreamConsumer._accept -> TypeError: unhashable type: 'list' at line 206.
            _read_until (lines 157-172) catches only OSError and HTTPException around the read loop,
            so the TypeError escapes run() and the process stops. The pending batch is not
            landed; the replay resends it on restart, because the checkpoint is not advanced.
            `wiki` as an object, `namespace` as a string and `server_name` as a number did not
            crash in the probe.
    Contradicts: the `_skip` docstring ("so one bad event does not stop the stream") and
            DECISIONS ("One malformed event ... was skipped and logged").
    Ask   : Validate every field the flatten and the filters touch, or wrap per-event processing
            in try/except that calls _skip. Add a test with a non-string type.

            http.client.BadStatusLine, which is an HTTPException).
    Proof : A server answering "NOT HTTP AT ALL" makes run() raise BadStatusLine.
    Ask   : Catch HTTPException on connect and reconnect like any other drop.

M2. mart_award_fy2024 grain is not a function of the award.
    Where : transform/models/marts/mart_award_fy2024.sql lines 9-11 (any_value of agency_code,
            state_fips, county_fips).
    Proof : Two awards in the FY2024 data span places:
              ASST_NON_FEL29493424_418 : county 09009 (1 row) and 09170 (2 rows)
              ASST_NON_21FXDWY001_485  : state 35 (1 row) and 56 (2 rows)
            any_value returns an arbitrary member, and with threads = 4 the choice can change
            between builds (DuckDB does not promise which member it returns; I did not reproduce
            a change). check_rerun.py compares only mart_monthly_obligations, so a change here
            would not be caught. The mart's own description ("one award") and DECISIONS do not disclose it.
    Ask   : Pick a documented rule (for example the place with the largest obligation, with a
            tie-break), or make the mart grain award-by-place. Add a test that the choice is
            deterministic.

M3. The 2021 fallback population sits under a 2024 name, and the mart does not say so.
    Where : transform/models/staging/stg_census_counties.sql line 22
            (`cast(POPESTIMATE2021 as integer) as population_2024`); dim_place passes it through;
            mart_monthly_obligations.sql line 28 exposes it as county_population_2024; the mart
            has no population_year column.
    Proof : Six Connecticut counties (09001, 09003, 09005, 09009, 09011, 09013) carry 2021 values
            in a column named population_2024 and in county_population_2024. The DECISIONS per-person
            definition says "the county's July 1, 2024 population". The top ten does not include
            them, so check 2's answer is not affected, but a reader of the mart cannot tell.
    Ask   : Expose population_year in dim_place and in the mart, or rename the column, and say so
            in the mart description.

M4. The 5-second flush does not fire when only heartbeats arrive; the deadline can overrun.
    Where : _batch_full is checked only after an accepted event (line 169); _lines checks the
            deadline only between lines, and readline can block for socket_timeout (5 s default).
    Proof : Probe: one event, then heartbeats every 0.5 s, batch_seconds 0.5. The only flush came
            at t = 4.0 s (the deadline), with 1 pending row. A silent stream with DURATION 1.0 and
            socket_timeout 3.0 ran for 3.24 s.
    Impact: Pending events are held in memory until the deadline or 2000 events. Nothing is lost,
            because the checkpoint is not advanced and the replay resends them, but the DECISIONS
            claim ("flushed ... every 5 seconds") is false, and "stops at DURATION" is off by up to
            one socket timeout.
    Ask   : Check batch age on heartbeats and on the timeout path too; correct DECISIONS, or bound
            the overrun.
