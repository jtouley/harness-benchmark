Verdict
The batch half (USAspending, Census, sitematrix, the monthly and award marts) is numerically sound on the data I checked.
The stream consumer is not ready. A single malformed event can kill the run, and a malformed HTTP status line can too.
Several published-contract issues need a decision or a fix before this is accepted.

Severity key: HIGH = crash or wrong output on plausible input. MEDIUM = wrong or misleading published data, or a
documented behavior that does not hold. LOW = latent, cosmetic, or test hygiene.


HIGH
----

F1  One malformed event kills the stream run (crash, not skip)
    Where: pipeline/stream_consumer.py line 200 (event_id in self.seen), line 206 (row["type"] in EDIT_TYPES),
           and the docstring at line 271 that says one bad event does not stop the stream.
    What: _field_problem (lines 253-267) only checks timestamp, length and meta type. Fields used as set or dict keys
          or sent to the pipeline are not checked.
    Verified:
      - type = ["edit"] -> TypeError: unhashable type: 'list', propagates out of run(). Run aborts.
      - meta.id = ["x"] -> TypeError in _accept (direct call). Run aborts.
      - namespace = 10**30 -> dlt raises PipelineStepFailed at step=extract when the batch is flushed. Run aborts.
    Tests: test_stream_consumer.py lines 69-81 cover only length and timestamp.
    Author fix: validate every field the consumer uses (type and meta.id str; namespace in bigint range; wiki and
    server_name str or null; bot coerced consistently) and add one test per field.

F2  Malformed HTTP status line escapes and kills the run
    Where: pipeline/stream_consumer.py lines 157-160. Only OSError is caught around _connect(). The HTTPException
           catch at line 171 is inside the read loop, not around the connect.
    Verified: a server answering "HTTP/1.1 ??? broken" raises http.client.BadStatusLine out of run().
    Author fix: catch (OSError, http.client.HTTPException) at line 159 and add a test with a raw socket server.


MEDIUM
------

F3  Time-based batch flush does not run during heartbeat-only stretches
    Where: pipeline/stream_consumer.py lines 169-170 and 214-217. _batch_full() is only evaluated after an accepted
           event. Heartbeat lines produce no (id, data) tuple, so the check is never reached in a quiet stretch.
    Verified: one event, batch_seconds=0.2, then heartbeats only. The flush happened at 1.56 s (the deadline),
              not near 0.2 s.
    Spec/doc conflict: DECISIONS.md line 73 says a batch is flushed "every 5 seconds".
    Consequence: events sit in memory until the next event or the deadline. A kill in that window loses them from the
                 lake until a replay resends them. Recovery depends on the replay, which is not guaranteed.
    Test gap: test_consumer_heartbeatsOnly_stopsAtDuration (test_stream_consumer.py lines 83-91) checks only that the
              run stops, not flush latency.
    Author fix: evaluate the time check inside _lines or the read loop on every line, and add a flush-latency test.

F4  DURATION is overrun by up to SOCKET_TIMEOUT on a silent stream
    Where: pipeline/stream_consumer.py line 25 (SOCKET_TIMEOUT = 5.0) and line 278 (readline blocks).
    Verified: silent stream, duration=1.0, socket_timeout=5.0 -> run took 5.00 s.
    Build log is consistent: make stream DURATION=90 exited after 99.4 s, which includes dbt, so the consumer ran about
    95 s.
    DECISIONS.md says the consumer stops when DURATION elapses. It does not, by up to 5 s.
    Author fix: set the socket timeout to min(SOCKET_TIMEOUT, time remaining), or document the overrun.

F5  The stream checks answer for whatever is in the lake, not for "the replayed hour"
    Where: DECISIONS.md lines 80-86 (data step and "The stream tests and marts read the lake as it stands"), and the
           marts that read lake/stream_* (fact_edit.sql, macros/stream_raw_arrivals.sql).
    What: checks 5 to 7 are computed over every event in the lake. The one build in build.log ran make stream
          DURATION=90, not a 3600 s hour. The DECISIONS figures (21,502 events, 3,603 s event span) come from a run that
          is not in this build log.
    Consequence: the answers depend on run history, not on the hour that A-18 names.
    Needs a decision by the author. The spec is not in the repo, so I cannot check which scope A-18 requires.
    Author fix: either bound the marts to an explicit run window recorded in the lake, or state in DECISIONS that the
                marts cover all landed events and that the graded hour is the only run.

F6  Published county and state population columns hold 2021 values for six Connecticut counties, with no year column
    Where: transform/models/marts/mart_monthly_obligations.sql line 16 (county_population_2024) and line 28
           (p.population_2024 from the 2021 fallback in stg_census_counties.sql line 22). Contract in
           transform/models/schema.yml lines 59-61.
    Verified: awards use 09001 (959768), 09003 (896854), 09005 (185000), 09009 (863700), 09011 (268805), 09013 (150293).
              These are 2021 values in a column named *_2024. The mart has no population_year column.
    Effect now: check 2 is unaffected (verified: no Connecticut county is in the top ten).
    Author fix: add county_population_year (and state population year) to the mart and its contract. Keep the existing
                column names, because oracle_map.yml check 2 names them.

F7  Territory states are labelled UNKNOWN
    Where: transform/models/star/dim_place.sql line 21, coalesce(s.state_name, 'UNKNOWN').
    Verified: the Census files have no rows for states 60, 66, 69, 72, 78. Awards have 138 transactions there (72: 75,
              66: 25, 78: 15, 69: 12, 60: 11). Their state_name becomes UNKNOWN, the same label as a missing state
              (A-12). Their county_name is NULL, not UNKNOWN, so the rows are also inconsistent.
    Author fix: give territories a fixed name table, or state explicitly in DECISIONS that the name is not in the
                Census files and use a distinct label.

F8  mart_award_fy2024 publishes an arbitrary place for awards whose transactions differ in place
    Where: transform/models/marts/mart_award_fy2024.sql lines 10-11 (any_value of state and county).
    Verified: two awards have transactions in different places:
              ASST_NON_FEL29493424_418 (09009 and 09170)
              ASST_NON_21FXDWY001_485 (state 56 and state 35)
    any_value has no defined order. The rerun check (tests/check_rerun.py line 15) compares only
    mart_monthly_obligations, so a changed value would not be caught.
    Author fix: pick a deterministic rule (for example the place of the latest action date) and document it, or drop
                the place columns from this mart.
