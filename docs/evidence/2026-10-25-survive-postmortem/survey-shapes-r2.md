# Survey: the 10 shapes-r2 Cadence runs other than P1 core-6

Scope: 10 runs in batch `2026-10-24-shapes-r2` (`batches/2026-10-24-shapes-r2.json`). P1 core-6 is excluded because it already had a full review, and P1 full-5 is excluded because it was lost (postmortem Oct 24 entry: "All 12 shapes-r2 runs are now accounted for: 11 scored, 1 lost (P1 full-5)"). This is a read-only survey. Nothing was re-run except reads of the stored trees and transcripts.

The stream trap the grader injects (`golden/pipeline/pipetask/schedule.py:175-185` @ c344bea) is F5. At a random position in the middle half of the stream, the replay sends one frame whose data is the first half of the next frame's JSON, carrying the previous position's id timestamp. A consumer that reconnects with `Last-Event-ID` set to the last good id resumes at or before that frame, so the server sends the same cut frame again. `stream_ok` requires the server to have served past the held-back late batch (`trial.py:267-271`), here position 11,774.

## Roll-up

### Money placement: holds in every run (verified)
All 10 trees place money by place of performance, and none uses recipient columns. The only "recipient" mentions are in DECISIONS.md or tests, explaining why recipient was not used (grep, table above). P1 core-6 does the same (`t1/explain-t1.md` "Things to know" 1). The prompts for P1 and P2 both carry the same place-based checks 2 and 4 (`golden/pipeline/P{1,2}/prompt.md:63,65`) and neither names a basis. Both hidden references choose place of performance (`reference/DECISIONS.md:14` P1, `:16` P2). Choosing place of performance is therefore not a scoring defect. The size of the UNKNOWN share (about 79%, `T:P1-core-4@L2022`, `T:P2-core-5@L1505`) recurs, as it did in core-6.

### Stream: the F5 frame splits the runs cleanly (verified from code and the regrade)
- **Reached the end (4 runs: P1 full-6, P2 core-6, P2 full-5, P2 full-6).** Each skips or rejects the cut frame and **keeps reading the same connection**. P1 core-6 does the same (`t1/tree/pipeline/stream_consumer.py:163-167`).
- **Did not reach the end (6 runs).** Each stalled at positions 5,898 to 5,974 of 11,774 needed (rg). This matches the postmortem's "6 of 9 consumers loop or crash at about position 5900".
  - 4 runs reconnect from the last good id and are served the same cut frame again: P1 core-4, P1 core-5, P1 full-4, P2 core-5. Each DECISIONS.md states the false premise that the replay resends the cut event whole. The connection counts (11 to 107) show the reconnect loop. That this is the cause is **inferred**: it fits the schedule and the counts.
  - 2 runs crash: P2 core-4, P2 full-4.
- All six except P2 full-4 hit the cut frame in their own development transcript (cites above). P2 full-4 never streamed from the trap replay.

### core-6 patterns: which hold
1. **Fixes patch the instance, not the class. Holds (5 runs).** P1 core-5 fixed the UTF-8 cut (MF-1) and left the bad-JSON loop (N-2) in the same handler. P1 full-6 fixed server_name (MF-1), then no-meta (F15, b4237df), one shape at a time. P2 full-5 fixed UTF-8 and non-event JSON in separate commits (839aa5d, 3e8496b). P2 core-6 fixed non-object JSON (MF-1). Counter-example: P2 full-6 MF-2 asked for the class fix ("treat both cases as malformed") and 677fd15 shipped it.
2. **Success claimed without observed output. Holds (5 runs).** Two forms:
   - Not run: P1 core-4 R1 c109 ("not run separately") and P1 full-4 R1 c97.
   - Observed only against a fake that resends the full frame: P1 core-4 R2 c41 and P2 core-5 R2 c75.
   - In addition, P2 core-5 reported "ran as specified" (`T@L1505`).
3. **Real issues deferred as N-items with no deferral review. Holds (4 runs).**
   - P1 core-5 N-2 (the exact F5 loop, reproduced).
   - P2 full-4 follow-up (the malformed crash).
   - P2 core-4 N-1 to N-8.
   - P1 full-6 left 8 nits open.
   Every full-shape P8 register found has 0 approved rows. Verified for P1 full-4 and P1 full-6; the P2 full-5 and full-6 registers have no rows (deferral registers written in-run).
- **Other core-6 classes that recur:**
  - A silent exit 0 when the stream cannot be reached was flagged in 6 records: P1 core-4 R1 c105 (judged a pass), P2 core-4 N-1, P1 full-6 F09, P2 core-5 F03, P2 core-6 F03, P2 full-4 F07.
  - No User-Agent header (core-6 H1). Four consumers use raw `http.client` and set none: P1 core-4, P1 core-5, P2 core-6, P2 full-4 (Connect calls listed above). The other six send a library default User-Agent. Whether the live endpoint accepts that default is **not verified**, because network access was not allowed.
  - Stream marts break on empty input (as with core-6 M2) in P1 full-4 (glob over a missing late_events file) and P1 full-6 (NOT NULL on late_events). The link to the dbt-duckdb empty-external placeholder row is **inferred**.

### One-offs
- P2 full-5's 0 comes from the oracle map shape, not the stream. Calling it a grader shape mismatch is **inferred**, per the postmortem's Oct 24 22:00 entry.
- The record and transcript disagree on the stop for P1 full-6 and P2 core-4.
- P2 full-6's regrade gives 3 against the official 2.
- P2 full-4 deliberately chose crash-on-malformed (DECISIONS.md:98).

### What the 0-score runs share
There are 7 zero-score runs. 6 of them have stream_ok false from the F5 frame (reward voided, `trial.py:189-191`). In all 6:
- the consumer reconnects or crashes instead of skipping;
- neither R1 nor R2 made it a must-fix;
- the run reached R7, or stopped elsewhere, without the stream defect blocking it.

In 3 of those runs the review records the behaviour: P1 core-5 R1 reproduced it, P2 core-4 R2 called it "fail closed", and the P2 full-4 R1 follow-up names it. The 7th run, P2 full-5, is the oracle-map one-off.

## Verified vs inferred
- **Verified** (read in the stored tree, transcript or record): placement columns; the consumer code paths; DECISIONS text; R1 and R2 contents, fix commits and stop points; that each run met F5 in development.
- **Secondary**: served positions, connection counts and stream logs come from another session's regrade (rg). Its passed counts match the official counts in 9 of 10 runs.
- **Inferred**:
  - That the reconnect loop is the cause of the stall, from the schedule code and the connection counts.
  - The cause of P1 core-5's development count of 18,136.
  - That the live User-Agent would be rejected.
  - The empty-mart mechanism in P1 full-4 and P1 full-6.
  - That P2 full-5 is an opinion mismatch.
  - That the graded tree equals the bundle HEAD: the bundles have no `refs/graded`, and the regrade reproduced the official passed counts.
